# UGREEN NAS（UGOS）Docker GUI だけで MyKakeibo を更新する手順

対象: UGOS の Docker アプリで kakeibo を運用している場合
前提: SSH を使わない / アプリのデータ（家計簿DB）は消さない

---

## 0. 最初に知っておくこと（今回のトラブルの原因）

| 症状 | 原因 |
|---|---|
| `/volume1/docker/kakeibovs` が存在しない | UGOS の「プロジェクト」は、作成方法によっては**指定フォルダを持たず GUI 内部で compose を管理**する。パスを前提にした CLI 手順は使えない |
| プロジェクトが2つある | 過去のプロジェクトが残ったまま、新しいプロジェクトで動いている。**ポート 9090 は1つしか使えない**ので、古い方が動いていると新しい方が起動できない |
| `update-nas.sh` で更新されない | スクリプトは「カレントフォルダの compose」を操作する。GUI のプロジェクトとは**別プロジェクト**を作ってしまうため、GUI 側のコンテナは古いまま残る |
| バージョンが 1.2.5 のまま | 実際に動いているコンテナが古いイメージを参照している（pull されていない／再作成されていない） |

**結論: GUI で作ったプロジェクトは、GUI で更新する。** これが最短で確実。

### 用語の関係

```
プロジェクト（compose のまとまり）
  └─ コンテナ（実際に動く箱。ポート 9090 を使う）
        └─ イメージ（ghcr.io/higemaguro/kakeibo:1.3.1 ← 版数はここ）
              └─ 家計簿DB は イメージの外（ボリューム）にあるので、更新しても消えない
```

---

## 1. 更新前の確認（3分）

### 1-1. どのプロジェクトが動いているか

`Docker` → **プロジェクト** を開き、状態が「実行中」のものを確認する。

- 実行中が1つだけなら、それが更新対象
- 2つ実行中なら **ポートが違う**はず。ブラウザで開いている `http://<NAS>:9090` がどちらかを確認する

### 1-2. どちらのプロジェクトが家計簿DBを持っているか

アプリの「データ管理」ページを開き、**取引が表示されている**ことを確認する。
（プロジェクト詳細の「ボリューム」に `data` フォルダの割り当てがある）

> ここが空なら、そのプロジェクトは別のデータを見ています。更新しても意味がないので、取引が見えるプロジェクトを対象にしてください。

### 1-3. バックアップ（GUIだけで完結）

アプリの **データ管理** ページで:

1. **JSON バックアップをダウンロード**（全データ。復元用の控え）
2. 必要なら **Excel ファイルをダウンロード**（月次の控え）

> GUI 更新では `update-nas.sh` の自動バックアップは走りません。この2つが代替です。

---

## 2. 古いプロジェクトの整理（任意だが推奨）

1. `Docker` → プロジェクト → **古い方**（動いていない／古い版）を選ぶ
2. **停止**（Stop）

**削除はしないでください。** 削除するとそのプロジェクトのボリューム（DB）も消える場合があります。
「1-2」で取引が見えているのが新しい方だと確認できた場合だけ、後日削除して構いません。

---

## 3. 更新手順（GUI のみ）

例: `1.3.0` → `1.3.1` に上げる場合。読み替えてください。

### Step 1. イメージを取得する

`Docker` → **イメージ** → 「取得（Pull）」:

```
ghcr.io/higemaguro/kakeibo:1.3.1
```

- 成功するとイメージ一覧に `1.3.1` が増える
- 失敗する場合:
  - `manifest unknown` → そのタグはまだ GitHub Actions でビルド中/失敗。Actions が緑になるまで待つ
  - `unauthorized` → GHCR が Private。`Docker` → レジストリ に `ghcr.io` のユーザー名（HigeMaguro）と PAT を登録する

### Step 2. compose の image 行を書き換える

`Docker` → **プロジェクト** → 対象プロジェクト → **Compose設定（編集）**:

```yaml
services:
  kakeibo-app:
    image: ghcr.io/higemaguro/kakeibo:1.3.1   # ← ここだけ変更
    container_name: kakeibo
    restart: unless-stopped
    ports:
      - "9090:80"
    volumes:
      - ./data:/app/data
      - ./backups:/app/backups
    environment:
      - TZ=Asia/Tokyo
```

- **変更するのは image のタグだけ**。`volumes`（`./data:/app/data`）は絶対に消さない
- 保存（Save）

### Step 3. 再デプロイ

同じプロジェクトの **「再デプロイ」**（または「再作成」「適用」）を実行する。

- 内部で「pull → コンテナ削除 → 新イメージで作成 → 起動」が行われる
- 1〜2分待つ
- もし「ポートが既に使用中」と出たら → §2 の古いプロジェクトが動いていないか確認して停止

### Step 4. 確認（3点）

1. `http://<NAS>:9090` を開く（**Ctrl+F5** で強制再読み込み）
2. ヘッダーのページ名の右が **`Ver：1.3.1`** になっている
3. 「データ管理」を開き、**取引データが表示されている**（＝DBは無事）＋ アプリバージョンが 1.3.1

> ヘッダーのバージョンはサーバーの `/api/version` を表示しています。ここが新しくなっていれば、確実に新しいイメージで動いています。

## 4. うまくいかないとき

### 4-0. 「プロジェクトの展開に失敗しました」＋ `manifest unknown`

**意味**: 指定したタグのイメージが GHCR にまだ存在しない（ビルド未完了／失敗）。

1. GitHub → **Actions** →「Docker publish」の該当タグの実行が **Success** か確認
2. 失敗/停滞している場合は **Re-run all jobs**（実行ページ右上）
3. それでも進まない場合は、**公開済みのタグ**に戻して再デプロイ（サービス復旧を優先）

```
image: ghcr.io/higemaguro/kakeibo:1.3.0   # 直近の公開済みに戻す
```

> 失敗しても **DBは無事**です（`./data` はイメージの外）。プロジェクトが「展開に失敗」状態でも、
> タグを戻して再デプロイすれば元通りになります。

### 4-1. 設定ファイルのパスは「プロジェクト詳細」に表示される

プロジェクトを開くと上部に **設定ファイルのパス**（例: `共有フォルダ/docker/kakeibo-vscode/docker-compose.yml`）が出ます。
`/volume1/docker/kakeibovs` のような**推測パスは使わない**でください（存在しないことがあります）。

CLI を使う場合も、**このパスをそのまま指定**します:

```sh
docker compose -f "/volume1/<共有フォルダ>/docker/kakeibo-vscode/docker-compose.yml" pull
```

| 症状 | 確認 | 対処 |
|---|---|---|
| 再デプロイ後も古い版のまま | イメージ一覧に新タグがあるか | 無ければ Step 1 の Pull が失敗している。あるのに古いなら「再作成」を明示実行、それでも駄目ならコンテナを削除してプロジェクトを「起動」 |
| `port is already allocated` | プロジェクト一覧の実行中件数 | 古いプロジェクト／古いコンテナを停止。`コンテナ` タブに残骸があれば削除 |
| `manifest unknown` | GitHub の Actions | 「Docker publish」が Success になるまで待つ（タグと `package.json` の版が一致しないと失敗する） |
| データが空になった | プロジェクト詳細のボリューム | 別の `data` を見ている。正しいプロジェクトのボリューム設定に戻す（DB自体は消えていない） |
| 起動はするが画面が古い | ブラウザキャッシュ | Ctrl+F5。HTML/JS は no-cache だが念のため |
| ログイン（認証）を求められる | GHCR が Private | `Docker` → レジストリ に PAT（read:packages）を登録 |

---

## 5. 元に戻す（ロールバック）

1. Compose設定の image タグを戻す（例 `1.3.0`）
2. 再デプロイ

DB はスキーマが後方互換（カラム追加のみ）なので、旧版に戻してもそのまま動きます。
DB も戻したい場合だけ、更新前にダウンロードした JSON を使ってください（通常は不要）。

---

## 6. おすすめの運用

- **プロジェクトは1つに統一**する（古いものは停止して残す。データ確認後に削除）
- タグは `latest` ではなく **版数固定**（`1.3.1`）にする → 何が動いているか明確、戻しやすい
- 更新のたびに「データ管理 → JSON バックアップ」を1回取る
- 更新後の確認は「ヘッダーの `Ver：`」「データ管理の版数」「取引が見える」の3点
- どうしても CLI を使いたい場合のみ: プロジェクト詳細に表示される compose のパスで `docker compose -f <そのパス> pull && up -d --force-recreate` を実行する（別フォルダで実行しない）

---

## 7. チェックリスト（印刷用）

```
□ 実行中プロジェクトを特定した
□ 取引が見えるプロジェクト＝更新対象だと確認した
□ JSON バックアップをダウンロードした
□ 新しいイメージを Pull した（イメージ一覧で確認）
□ Compose設定の image タグを変更した（volumes は触っていない）
□ 再デプロイした
□ ヘッダーが Ver：新バージョン になった
□ データ管理で取引が見える／版数が一致
□ 古いプロジェクトを停止した
```
